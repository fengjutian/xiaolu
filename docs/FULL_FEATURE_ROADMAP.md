# 小鲁 System Lens：完整功能规划

版本：0.4 规划稿
状态：实施中（0.49.0 二十三个工具 + 4 个内置页）
目标平台：Windows 10/11 x64  
桌面框架：Tauri 2 + React + Rust

## 1. 产品目标

建设一个本地优先、透明、可审计的 Windows 硬件检测与系统维护工具，覆盖鲁大师同类产品的主要使用场景：硬件识别、温度监控、磁盘健康、性能测试、驱动检测、系统监控、启动项与基础诊断。

后期增加 AI 诊断层，把结构化检测数据转化为有证据、可追溯的解释和排障建议。AI 不替代本地健康规则、安全策略和用户授权，详细规划见 [AI_REQUIREMENTS.md](AI_REQUIREMENTS.md)。

这里的“复刻”定义为功能类别和用户流程的覆盖，不复制鲁大师源代码、商标、图标、文案、私有协议、私有驱动或评分算法。评分结果不得宣称与鲁大师分数等价。

v0.25.0 新增（GPU 计算跑分）：

- GPU 跑分从 WebGL2 升级为 **WebGPU 计算管线**；Windows 上由 Chromium 的 D3D12
  后端执行，符合“GPU 用 D3D12”的目标
- 工作负载：2M 个 u32、每线程 1024 次混合运算、8 个批次；读取校验和防止被优化
- 记录适配器信息（如 `intel / xe-lpg`）、工作负载参数与 backend 标记
- 分数归一化到与 WebGL2 同数量级，说明中注明“仅同版本比较”
- WebGPU 不可用或初始化失败时自动回退 WebGL2，并在 note 中标明回退
- 取消：WebGPU 在批次之间检查取消标志；WebGL2 路径仍不可中断
- 实机验证：WebView2 提供 `navigator.gpu`，Intel Xe LPG 适配器跑分成功，
  结果 note 为“WebGPU 计算管线（Windows 由 D3D12 后端执行）”

v0.34.0 新增（P1 写操作框架与首批写工具）：

- 宿主侧：写动作必须清单声明 `write: true`、非只读、携带令牌；令牌一次性使用；

- `lockscreen`：预览后确认调用 `LockWorkStation` 锁定当前会话
- `pc_optimizer`：枚举电源计划（`PowerEnumerate`/`PowerGetActiveScheme`），
  预览后确认切换活动计划（`PowerSetActiveScheme`），原计划写入操作日志
- 操作审计：`%LOCALAPPDATA%\SystemLens\tool-actions.jsonl`，只记录工具、动作、
  对象标识、时间与结果，不记录用户内容
- 工具箱累计 **16 个可运行工具**（14 只读 + 2 写），规划中 **15 项**
- 验证：`lockscreen` 预览签发令牌、篡改令牌返回 `INVALID_TOKEN`、缺失令牌返回
  `CONFIRMATION_REQUIRED`；`pc_optimizer` 计划枚举、令牌与计划列表绑定通过，

## 3. REA 证据边界

此前对安装器和安装目录的静态分析确认目标产品包含硬件检测、系统服务、网络下载、压缩处理、签名检查和多个独立模块；安装目录含大量 EXE、DLL 和 SYS 文件。这些是产品由多模块及特权组件构成的静态证据，不代表已经观察到每个功能的运行流程。

实施时遵循以下边界：

- 静态证据用于确定功能调查方向，不用于声称运行时行为。
- 每个兼容功能都必须由我们自己的接口、测试和运行记录验证。
- 不加载、不调用、不重新分发目标产品的 DLL、SYS、资源或接口。
- 后续若需精确对齐某一流程，先建立对应 REA Evidence ID，再单独记录观察、推断和未知项。

## 4. 目标架构

```text
React / Mantine UI
        │ Tauri IPC
        ▼
Rust application core
  ├─ snapshot service       CPU / memory / disk / network
  ├─ sensor service         temperature / fan / voltage / power
  ├─ storage health service SMART / NVMe health / reliability
  ├─ benchmark engine       CPU / memory / disk / GPU
  ├─ driver inventory       SetupAPI / CIM / signature / version
  ├─ diagnostics service    startup / services / events / network
  └─ local persistence      SQLite history / settings / results
        │
        ├─ Windows documented APIs
        ├─ optional signed sensor helper
        └─ explicitly approved elevated operations
```

### 权限分层

1. 普通用户只读：默认模式，完成大部分信息采集。
2. 管理员按次授权：读取受限 SMART、控制传感器辅助组件、导出高级诊断。
3. 系统修改：驱动安装、服务修改、清理删除等必须逐项确认，并提供恢复点或回滚信息。

应用不得为了展示信息而默认常驻管理员权限。

| 模块 | 功能 | 首选实现 | 权限 | 验收标准 |

| 温度传感器 | 告警与曲线 | SQLite 时序数据 + 桌面通知 | 普通 | 阈值可配置，休眠恢复后不误报 |
| SMART | SATA SMART 属性 | smartctl 适配层或 Windows Storage API | 普通/管理员 | 展示原始值、阈值和来源，不只给单一健康百分比 |
| SMART | NVMe Health Log | NVMe/Storage Management API 或 smartctl | 普通/管理员 | 温度、寿命百分比、读写量、错误计数可读取 |
| SMART | 健康判断 | 规则引擎，区分正常/注意/危险/未知 | 普通 | 未支持设备必须显示“未知”，不得误判为健康 |
| 性能跑分 | CPU 单核/多核 | Rust 固定工作负载、线程亲和与预热 | 普通 | 同机连续 3 次偏差目标小于 5% |
| 性能跑分 | 内存带宽/延迟 | Rust 顺序/随机读写与复制测试 | 普通 | 标明容量、线程、耗时与误差范围 |
| 性能跑分 | 磁盘顺序/随机 IO | 临时测试文件、可选盘、严格空间上限 | 普通 | 可取消，异常退出后自动清理测试文件 |
| 性能跑分 | GPU | Direct3D 12 compute/render workload | 普通 | 显示 GPU、驱动、分辨率和测试版本 |
| 性能跑分 | 综合评分 | 公开版本化公式与本机历史比较 | 普通 | 分数可重现，明确不等同于第三方评分 |
| 驱动检测 | 设备与驱动清单 | SetupAPI + `Win32_PnPSignedDriver` | 普通 | 设备、提供商、版本、日期、INF、签名状态完整 |
| 驱动检测 | 异常设备 | Configuration Manager / PnP 状态码 | 普通 | 能识别缺失、禁用、错误码和未知设备 |
| 驱动检测 | 更新建议 | Windows Update API + OEM 官方链接 | 普通 | 来源、版本、适用硬件 ID 和发布日期可追溯 |
| 驱动更新 | 下载/安装/回滚 | 后续阶段，签名和硬件 ID 双重校验 | 管理员 | 安装前确认，失败可回滚，默认不自动安装 |

## 6. 分阶段实施路线

### Phase 1：采集平台重构（1–2 周）

- 将 `system.rs` 拆分为 `snapshot`、`hardware`、`network`、`startup` 模块。
- 建立统一数据模型：值、单位、来源、时间戳、状态和错误。
- 使用 SQLite 保存最近 24 小时监控数据、用户设置和测试历史。
- 增加采集任务调度，避免 UI 轮询阻塞和多个采集器相互争用。
- 完成应用崩溃恢复、休眠/唤醒与设备热插拔处理。

交付标准：现有 v0.2.0 功能无回归，持续运行 8 小时无明显内存增长。

### Phase 2：温度与传感器（2–3 周）

- 新增 `sensor-helper`，优先使用 LibreHardwareMonitorLib 的公开接口。
- 定义 helper 与 Tauri 主进程之间的版本化 JSON IPC 协议。
- 展示温度、风扇、电压、功耗和时钟；没有数据时说明原因。
- 增加温度曲线、最大/最小值、阈值告警和托盘摘要。
- 对需要底层访问的硬件提供可选管理员启动，不默认安装内核驱动。

交付标准：覆盖 Intel/AMD CPU、Intel/NVIDIA/AMD GPU 的常见传感器路径；不支持设备不崩溃。

### Phase 3：SMART 与存储健康（2 周）

- 建立存储设备和卷的稳定映射，避免把分区误当物理磁盘。
- 读取 ATA SMART 和 NVMe Health Log。
- 展示通电时间、启动次数、温度、重映射扇区、不可校正错误、寿命和总读写量。
- 建立来源明确的健康规则，不伪造“精确剩余寿命”。
- 增加短测能力前先完成设备支持与风险评审；默认只读。

交付标准：SATA SSD/HDD 与 NVMe 各至少两类设备通过真实机器或固定采样测试。

### Phase 4：性能跑分（3–4 周）

- CPU：整数、浮点、压缩、哈希等固定工作负载。
- 内存：复制、读取、写入和随机访问。
- 磁盘：顺序/随机读写，测试大小默认 1 GiB，可配置上限。
- GPU：Direct3D 12 基础图形与计算测试。
- 提供单项分数、综合分数、原始指标、测试环境和历史对比。
- 跑分时暂停高频后台采集，显示温度和取消按钮。

交付标准：同机重复性、取消清理、低磁盘空间保护、笔记本电源状态提示全部通过。

### Phase 5：驱动检测（2–3 周）

- 枚举 PnP 设备、硬件 ID、INF、驱动版本、提供商和签名状态。
- 识别未知设备、错误设备、禁用设备和缺失驱动。
- 首版仅提供检测、导出和官方来源跳转。
- 第二版再接 Windows Update API，形成可验证的更新候选。
- 自动安装推迟到回滚、签名校验和恢复点机制成熟后。

交付标准：检测结果能与设备管理器交叉核对；建议不得仅依据“版本号更大”。

### Phase 6：同类产品完整覆盖（持续迭代）

- 电池健康、循环次数和充放电功率
- 显示器、音频、USB、蓝牙和摄像头信息
- 网络诊断、端口与连接进程、DNS/代理/Hosts 检查
- Windows 服务、计划任务、事件日志和蓝屏记录摘要
- 大文件、重复文件和磁盘空间分析
- 软件清单、卸载入口与残留扫描
- 节能/高性能模式建议、游戏模式和悬浮监控窗
- HTML/PDF 报告、设备对比和离线报告导入

系统清理、卸载、服务修改等写操作应作为独立模块，不能与只读检测混合授权。

## 7. 关键技术决策

### 7.1 温度 helper

Tauri 主程序保持 Rust；传感器使用独立 .NET helper 隔离第三方库、权限和崩溃。helper 只能输出传感器数据，不接受任意命令。发布前必须审查 LibreHardwareMonitor 的许可、依赖和可再分发文件。

### 7.2 SMART 后端

优先使用 Windows 文档化接口；覆盖不足时评估随应用分发 `smartctl`。若采用 smartmontools，必须在发布流程中满足 GPL 许可和源码提供义务。SMART 解析器使用固定 JSON 样本进行回归测试。

### 7.3 驱动来源

驱动建议只信任 Windows Update 或设备厂商官方来源。禁止使用来源不明的第三方驱动包，禁止静默安装，禁止绕过签名策略。

### 7.4 跑分可比性

建立 `benchmarkSchemaVersion`、工作负载版本、编译版本和硬件环境记录。公式公开且版本化；公式升级后旧分数不直接混合排名。

## 8. 数据与隐私

- 默认不联网、不上传硬件标识。
- 序列号、MAC、IP、主机名默认在报告中脱敏。
- 历史数据保存在用户本地应用数据目录。
- 远程更新检查和匿名遥测必须分别提供显式开关，默认关闭。
- 不把温度、进程、软件清单或驱动清单发送给第三方。
- AI 默认关闭；启用云端模型前展示发送数据的类型、服务商和用途。
- AI 发送载荷默认移除序列号、硬件 ID、主机名、用户名、MAC、IP、完整路径、进程命令行和事件日志全文。
- API 密钥使用系统安全凭据存储；模型不可直接访问文件系统、Tauri command 或任意网络目标。

## 9. 安全要求

- Tauri capability 保持最小权限，不增加任意 shell 执行能力。
- 外部 helper 使用固定绝对路径、哈希校验和版本握手。
- 所有管理员操作通过单独进程执行，并记录动作、目标和结果。
- 启动项、驱动、服务、文件清理修改前必须展示精确对象并二次确认。
- 下载物必须验证 HTTPS、发布者签名、文件哈希和硬件适用性。
- 跑分设置 CPU、内存、磁盘空间、耗时和温度安全上限。
- AI 只能调用宿主白名单内、参数经过 Schema 校验的工具；首版仅允许只读工具。
- AI 的文本输出不能作为写操作授权，所有写操作仍须本地 UI 二次确认和有效确认令牌。
- 事件日志、文件名和软件名称等外部内容视为不可信输入，不得改变工具权限或系统指令。

## 10. 测试策略

### 自动测试

- Rust 数据模型、SMART 解析、评分公式和启动项事务单元测试
- 传感器/驱动/SMART 固定样本测试
- Tauri command 集成测试
- React 页面、空数据、错误和取消流程测试
- 长时间采集、内存泄漏和数据库保留策略测试

### 硬件矩阵

- Intel/AMD CPU
- Intel/NVIDIA/AMD GPU
- SATA HDD、SATA SSD、NVMe SSD、USB 存储
- 台式机、笔记本、虚拟机
- Windows 10 22H2、Windows 11 当前受支持版本

### 交叉验证

传感器、SMART 和驱动信息至少与 Windows 自带工具及一个可信独立工具比对。差异必须记录原因，不通过简单平均掩盖冲突。

## 12. 暂不承诺的功能

- 与鲁大师分数一一对应
- 使用或兼容鲁大师私有内核驱动
- 绕过 Windows 驱动签名或安全机制
- 自动安装来源不明的驱动
- 在缺少硬件数据时推断温度或伪造健康状态
- 未经确认执行驱动、服务、启动项或文件修改
- AI 生成或执行任意 shell、PowerShell、注册表脚本或未经审核的下载地址
- 在缺少证据时由 AI 生成确定性故障、寿命或修复结论

## 13. 下一步实施清单

开始编码时按以下顺序执行：

1. 重构 Rust 采集模块并引入 SQLite。
2. 建立 `sensor-helper` 原型和 IPC 协议。
3. 完成 CPU/GPU/磁盘温度卡片与历史曲线。
4. 评估 Windows Storage API 与 smartctl 的真实设备覆盖率。
5. 建立 SMART 样本库和规则测试。
6. 实现 CPU 跑分的第一个可重复基准。
7. 建立驱动清单和异常设备只读页面。
8. 建立统一诊断事实和不可变快照协议，作为后期 AI 与规则诊断的共同输入。
9. 完成 AI 数据脱敏、Provider 接口和只读工具白名单设计后，再进入健康解读 MVP。

任何需要内核驱动、管理员安装或第三方二进制分发的决策，都应在进入实现前单独提交依赖、许可、安全和回滚评审。
